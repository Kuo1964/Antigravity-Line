診斷結果與修復導入計畫 (Implementation Plan)

🔍 診斷原因 (Root Cause Analysis)

經過 `/diagnosing-bugs` 的反饋迴圈探查，精確定位第二個問題發送後卡住的三大根本原因：

1. 大檔案上下文過載與模型推論延遲 (Prompt Bloat & Latency)：

  • 目標專案 `Portugal_Paris-2026` 內包含多個大型 Markdown 行程檔案（如 `gmail_portugal_updates.md` 達 101KB，`2026_葡萄牙巴黎17天每日詳細行程總彙整.md` 達 13KB）。
  • 之前設定自動讀取多個文件檔，導致傳給 Gemini API 的 Prompt 高達萬字以上，推論時間大幅增長（15 ~ 30 秒）。

2. Google Search Grounding 工具觸發額外延遲與可能之連線逾時：

  • 預設開啟 `types.GoogleSearch()` 即時連網，模型針對長行程規劃同時進行網路搜尋比對，造成 API 生成耗時過長甚至連線中斷。

3. 鎖（Mutex Lock）與防禦釋放保護不足：

  • 當背景任務在 Gemini API 超時或發生例外時，若 Task 超時被取消，可能導致該使用者的 `asyncio.Lock` 卡在 `locked()` 狀態，導致後續所有新傳送的訊息皆被互斥鎖靜默攔截。

🛠️ 擬定修復方案 (Proposed Changes)

1. 智慧文檔過濾與優先級裁剪 ([app/project_manager.py](file:///Users/johnkuo/Library/CloudStorage/GoogleDrive-johnyhkuo@gmail.com/我的雲端硬碟/worktemp/Antigravity-Line/app/project_manager.py))

  • 優化：優先搜尋與 Prompt 最相符的核心檔（如帶有 `行程`、`Itinerary`、`SUMMARY` 或 `README` 的 Markdown 檔），過濾掉超過 50KB 的歷史 Log/更新檔 (如 `gmail_portugal_updates.md`)。
  • 長度限制：單個文檔內容截取上限降至 2,500 字，總上下文控制在黃金長度內，讓 Gemini 能在 3~5 秒內快速響應。

2. 智慧工具調用適配 ([app/services/agent_session_engine.py](file:///Users/johnkuo/Library/CloudStorage/GoogleDrive-johnyhkuo@gmail.com/我的雲端硬碟/worktemp/Antigravity-Line/app/services/agent_session_engine.py))

  • 優化：當已有專案文件上下文時，預設不強制開啟 `GoogleSearch`（除非 Prompt 顯式要求「上網查」或「最新新聞」），大幅縮短 API 推論時間。
  • Timeout 防禦：為 Gemini SDK 呼叫加入 25 秒 `asyncio.wait_for` 逾時控制，逾時自動降級推播說明。

3. Mutex 鎖超時自動解鎖機制 ([app/main.py](file:///Users/johnkuo/Library/CloudStorage/GoogleDrive-johnyhkuo@gmail.com/我的雲端硬碟/worktemp/Antigravity-Line/app/main.py))

  • 優化：為 `user_locks` 加上 45 秒強制解鎖防護（Auto-release Safety Guard），確保即使背景 Task 發生罕見崩潰，鎖也會自動釋放，絕不卡死後續訊息。
