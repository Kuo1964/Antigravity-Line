LINE Desktop (Mac) 自動化穩定性完整評估報告

根據您的要求，我對目前「依賴滑鼠座標點擊」的自動化方式進行了完整的穩定性評估，並探索了更好的替代方案。

1. 目前作法的穩定性評估 (滑鼠座標點擊)

目前的腳本是透過 `取得視窗位置與大小 (x, y, w, h)`，再加上固定的偏移量（例如 `win_x + 190`）來決定點擊位置。

結論：這個方法「非常脆弱」，確實會受到視窗大小與版面變化的嚴重影響。

脆弱點分析：

1. 內部窗格縮放 (Pane Resizing)：LINE 的左側（聊天室清單）與右側（對話視窗）之間有一條分隔線是可以左右拖拉的。如果使用者把左側拉寬，原本寫死的 `win_x + 190` (搜尋框位置) 可能就會點偏。

2. 作業系統陰影與邊界 (OS Shadow/Padding)：如同早上發生的 Bug，macOS 會將視窗邊緣的透明陰影算進 `win_h` 裡。且不同版本的 macOS 或不同的外接螢幕 (Retina vs 非 Retina)，陰影與縮放比例都可能不同，導致 `win_h - 60` 點到錯誤的工具列。

3. 介面更新 (UI Updates)：只要 LINE 稍微改版，增加上方選單的高度或下方工具列的大小，固定的像素偏移量就會立刻失效。

---

2. 探索「更好的辦法」

為了解決座標點擊的盲點，我針對 macOS 系統與 LINE App 進行了幾種自動化技術的底層測試：

❌ 方案 A：AppleScript 輔助使用 API (UI Scripting)

  • 概念：透過 macOS 原生的 Accessibility API，直接叫系統去點擊「文字輸入框」，這是 Mac 自動化最標準且無敵的做法。
  • 測試結果：失敗。LINE Desktop 採用了跨平台的 UI 框架（如 Qt/Electron），它並沒有把內部的按鈕與輸入框開放給 macOS 系統。在我剛才的背景測試中，系統讀取 LINE 的 UI 元素回傳的是「空清單」。系統就像瞎子一樣，看不到 LINE 裡面的任何按鈕。

❌ 方案 B：URL Schemes (深層連結)

  • 概念：使用類似 `line://msg/text/?text=...` 的連結直接喚起特定聊天室。
  • 測試結果：不適用。LINE 的 URL Scheme 大多需要知道目標的內部 `Room ID`，我們只知道對方的顯示名稱（如 "Sharon Chou"），無法直接透過連結搜尋名字。

💡 方案 C：全面改用「全鍵盤操作」+「自動對焦」(Keyboard-Only Navigation) —— **最佳解法**

  • 概念：捨棄滑鼠點擊，全程利用 LINE 的內建快捷鍵與介面邏輯來驅動。這完全無視視窗大小、比例、分隔線位置。
  • 作法：

1. 腳本打開 LINE 後，按下快捷鍵 `Cmd + 2` 確保切換到「聊天室」分頁。

2. 使用快捷鍵 `Cmd + F` (或依賴搜尋框的相對安全區域) 來啟動搜尋。

3. (關鍵) 透過剪貼簿貼上名字 `Sharon Chou` 後，直接按下 `Enter` 鍵！

4. LINE 的設計是：在搜尋結果按下 Enter 鍵，會自動開啟該聊天室，並且「打字游標會自動對焦在底部的輸入框」！

5. 既然游標已經自動對焦，我們完全不需要去算座標點擊輸入框（直接砍掉引發今早 Bug 的步驟 D），直接 `Cmd+V` 貼上圖片，再按 `Enter` 即可送出。

3. 總結與下一步建議

目前的「滑鼠座標法」就像是蒙著眼睛背步數走路，只要桌椅（視窗尺寸）稍微被移動，就會撞牆。

我建議的「終極改良版」工作流程：

1. 取消點擊輸入框：利用 LINE 開啟聊天室後「游標會自動 Focus」的特性，直接刪除點擊底部的危險動作。

2. 強制剪貼簿輸入：中文字全部透過「寫入系統剪貼簿 -> `Cmd+V` 貼上」來輸入，避開模擬打字的字元遺失問題。

這樣一來，不論您把 LINE 視窗拉得多大、多小、左邊多寬、右邊多窄，只要搜尋框還在左上角的大致範圍內，腳本就能 100% 成功發送。
