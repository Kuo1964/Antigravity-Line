診斷原因與修復導入計畫 (Implementation Plan)

🔍 診斷原因 (Root Cause Analysis)

透過實時追蹤器與本機腳本單獨模擬 `agent_manager.run_agent_task` 完整生命週期，徹底定位根本原因：

1. 推論解答長度高達 3,893 字，產出耗時 20~28 秒：

  • 針對 `Portugal_Paris-2026` 專案查詢行程時，Gemini API 生成的解答高達 3,893 個字元。
  • 因為解答極長，整套 API 呼叫、上下文注入與長解答生成需時 20~28 秒。

2. 同步 SDK 與步調間隔堵塞 Event Loop 觸發 45 秒 Task 超時取消：

  • 在 `deliver_text` 與 `process_background_agent_task` 中，`time.sleep(0.5)` 與 LINE Messaging API 的 SDK 調用皆為同步阻塞 Call。
  • 在多段連續推播 3,893 字解答時，同步阻塞加劇了 Event Loop 調度延遲，致使背景 Task 觸發 45 秒硬性超時取消，進而導致解答訊息無法完成推播。

---

🛠️ 擬定修復方案 (Proposed Changes)

1. 全面非阻塞異步化發送 ([app/services/line_delivery_adapter.py](file:///Users/johnkuo/Library/CloudStorage/GoogleDrive-johnyhkuo@gmail.com/我的雲端硬碟/worktemp/Antigravity-Line/app/services/line_delivery_adapter.py))

  • `deliver_text_async` 異步發送介面：將 LINE Messaging API 的 `push_message` 包裹於 `await asyncio.to_thread(...)` 中執行，並將多段推播間隔改為非阻塞的 `await asyncio.sleep(0.5)`，零堵塞 Event Loop。

2. 異步 Timeout 調整與長回應優化 ([app/main.py](file:///Users/johnkuo/Library/CloudStorage/GoogleDrive-johnyhkuo@gmail.com/我的雲端硬碟/worktemp/Antigravity-Line/app/main.py))

  • 將背景 Agent 任務的最大等待 Timeout 由 45 秒安全擴充至 90 秒，給予長篇行程解答充足且穩定的運算與多段發送時間。
  • 呼叫 `await line_delivery_adapter.deliver_text_async(...)` 確保多段推播順暢流出。
