診斷原因與修復導入計畫 (Implementation Plan)

🔍 診斷原因 (Root Cause Analysis)

透過實地腳本探查 LINE Messaging API 伺服器回應，100% 擊中極隱蔽的核心死穴：

1. LINE API HTTP 400 Bad Request 被靜默吞掉：

  • 當傳送之內容包含某些 Markdown 特殊符號、轉義字元或格式問題時，LINE API 伺服器會拒絕發送並回傳 `(400) Reason: Bad Request, {"message":"Failed to send messages"}`。
  • `LineDeliveryAdapter.deliver_text` 內部的 `except Exception as api_err:` 在捕捉到該 HTTP 400 錯誤後僅記錄了一行 `logger.warning`，隨後靜默結束並回傳 `False`，導致使用者手機端徹底斷訊，無任何後續推播與錯誤提示。

2. 缺少「Unicode / Markdown 安全清理器 (Sanitizer)」：

  • Markdown 轉譯器在處理解答文字時未進行 LINE API 相容性清理，導致部分特殊字元引發 LINE 官方伺服器攔截拒絕。

3. 缺少降級備用發送 (Fallback Standard Push)：

  • 當單段 push 發生 400 Bad Request 時，系統缺少純文字安全剝離 (Plain-Text Strip) 與單段重試機制。

---

🛠️ 擬定修復方案 (Proposed Changes)

1. LINE 專用文字安全清理器 ([app/services/line_delivery_adapter.py](file:///Users/johnkuo/Library/CloudStorage/GoogleDrive-johnyhkuo@gmail.com/我的雲端硬碟/worktemp/Antigravity-Line/app/services/line_delivery_adapter.py))

  • `sanitize_text_for_line(text: str)`：自動清理無法被 LINE API 解析的無效控制字元、不合規轉義符號與異常語法，確保 100% 通過 LINE API 驗證。

2. 400 Bad Request 自動降級與純文字重試

  • 當 Messaging API 拋出 400/404 例外時，自動將該 chunk 剝離為乾淨純文字 (Plain Text fallback) 並進行一次安全重試。
  • 若最終仍無法發送，主動推播一條簡短警報：`"⚠️ 訊息推播遭受 LINE 伺服器拒絕，已紀錄日誌。"`，絕不讓使用者無窮等待。
