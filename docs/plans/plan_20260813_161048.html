實作計畫：段落感知的步調化連續分推機制 (Paced Safe-Chunk Streaming Plan)

📌 背景與問題說明 (Background & Problem Statement)

當使用 LINE Bot 查詢大型專案（如 `Portugal_Paris-2026` 17天詳細行程）時，Gemini 生成的成果解答高達數千字。目前系統在發送長推播時存在以下瓶頸：

1. 硬性切割破壞語法：原先依硬性字數切割，容易撕裂 Markdown 卡片與標題，導致 LINE API 拋出 HTTP 400 Invalid Request 錯誤。

2. 密集發送引發 API 限流：在單次請求包含太多 chunks 或連續無間隔發送時，容易觸發 LINE API 頻率限制 (Throttling)，進而誤入會卡死好友搜尋的「桌面 GUI 降級」流程。

---

🛠️ 擬定變更內容 (Proposed Changes)

本計畫將在不動到任何發送早安圖片與排程邏輯前提下，升級 `LineDeliveryAdapter` 推播傳輸機制：

#### 升級 `split_text_chunks` 為智慧語意段落切割：

  • 安全邊界：優先依據雙換行 (`\n\n`)、段落標頭 (📌) 或 Markdown 區塊進行切割，確保單個 Chunk 不超過 1,800 字元（預留 200 字的安全 Padding）。
  • 完整性維護：保證每段訊息都是語意完整、格式美觀的 LINE 專屬卡片，不撕裂標題與代碼區塊。

#### 升級 `deliver_text` 為步調化獨立連續推播 (Paced Sequential Push)：

  • 獨立請求推送：不再將數千字打包在單一巨型 Payload，而是分割為多個獨立的 `PushMessageRequest`。
  • 0.5 秒步調控制：連續發送不同段落時，加入 `time.sleep(0.5)`（或異步 `asyncio.sleep(0.5)`），確保 LINE 伺服器輕鬆接單，讓使用者手機順暢跳出第一區塊、第二區塊等連續卡片。
  • 無效 GUI 降級保護：對於遠端 API 推播失敗的情況，記錄精確 Error 日誌並進行文字降級重試，絕不調用會卡死的好友搜尋 GUI。
